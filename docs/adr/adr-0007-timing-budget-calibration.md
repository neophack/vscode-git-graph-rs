# ADR 0007: The timing budgets' first calibration — engine-path pipeline medians, and what stays pending

Date: 2026-10-27
Status: Accepted (partial calibration record under ADR-0004's rule: budgets stay as written;
the rows measured here are confirmed achievable and may only tighten. Supersedes nothing —
ADR-0004's deferral stands for every row this record does not measure.)

## Context

REFACTOR-PLAN §3.8.1 requires the timing budgets to be **calibrated once** against real
measurements and recorded in an ADR, after which they may only tighten. ADR-0004 deferred that
calibration until the P-gate harness produced per-scenario P50/P95. Since then:

- **P1 landed** (wave 2): the T0–T5 markers and the operation spans (`op:loadCommits`,
  `op:commitDetails`, `op:loadRepoInfo`) in `src/shared/perf/trace.ts`, the host ring buffer,
  the `Trace ...` log lines under `git-graph-rs.enableLog`, and P50/P95 in
  `scripts/analyze-log.mjs`.
- **P2 landed** (this wave): the S/M/L fixture generator (task 0.5,
  `test/perf/fixture.mjs`), the P4 collection in the E2E launcher
  (`test/perf/collect-e2e-traces.mjs` + the entry's per-scenario windows), and the nightly
  S/M schedule in `.github/workflows/perf.yml`.

This record is the first calibration input: the P2 host-pipeline gate measured every §3.8.1
operation row the P1 markers cover, on the S tier, on the plan's "one Windows dev machine"
reference environment, with 21 samples per row, on BOTH read paths the extension ships.

## Measurement setup

- Commit `b8d7c44` (branch `task/w3-p2`), Windows 10.0.26200 x64 dev machine, Node 24, git
  2.50.1. Fixture: the S tier (1 K commits / 20 branches / 20 tags, seed 12345), generated by
  `node test/perf/fixture.mjs --tier s` (2.0 s; idempotent).
- Command: `node test/perf/p2-host.mjs --samples 21 --tier s --backend engine,cli --work-dir
  test/perf/fixtures/s` (results: `test/perf/results/p2-s.json`). The engine binary was a
  prebuilt `win32-x64-msvc` addon of the same day; the CLI numbers are the pure `git` fallback.
- What P2 measures is the **pipeline half** of each budget: the initial-response latency of the
  real `CommitLoader`/`GitRepository` pipeline — the moment the webview could start painting
  (§3.8.1's T3-side). The webview half (render-to-paint) is P3's; the in-editor whole-view
  numbers are P4's.

## Decision

1. **Every budget measured here is confirmed as written — on the engine path, at the pipeline
   half.** The engine medians fit the S budgets with 3–75× margin; adding P3's webview half
   (the T2→T5 "own time" slice, budget 80 ms) leaves room, which the nightly's whole-view
   numbers will confirm. **The budgets may only tighten from here.** Relaxing one requires a
   superseding ADR with the measurement context and the cost of the alternatives.
2. **The CLI fallback's numbers are recorded, and deliberately NOT made the calibration basis.**
   The CLI path misses every operation budget by 3–5×. That is the fallback being the fallback —
   the budgets bind on the shipped default path (the engine). Recording the CLI numbers here
   without relaxing anything keeps the "the view is slow" report honest when the engine is
   absent, without rewarding it with looser budgets.
3. **M/L tiers and the CI Linux environment are the nightly's job** (`.github/workflows/perf.yml`
   now runs P2 on S and M nightly, non-blocking, `--record`): the first M-tier P50/P95 will show
   whether the S-confirmed budgets scale as §3.8.1 assumed (M ≤ 600/250/80/100/100/200).

## What this record could not calibrate, and why

| Row | Blocker | Unblocks via |
|---|---|---|
| Whole-view T0→T5 (open ≤ 400 ms) as a single number | host and webview clocks are deliberately not synchronised (`src/shared/perf/trace.ts`); the log yields host T0→T3 and webview T2→T5 separately | the nightly's P4 traces (sum of halves) or P3's synchronised page measurement |
| Snapshot-first-paint (≤ 150 ms) | no marker exists for the snapshot paint (T5 marks the first commit rows, not the snapshot) | a T-snapshot marker (P-workstream follow-up) |
| Activation synchronous main-thread time (≤ 20 ms) | the ACTIVATION mark exists, but the budget names event-loop blocking, not a mark span | an event-loop-lag probe in P4 |
| In-editor T0–T5 / op traces (P4) on this machine | **found, not fixed — product defect**: the session logger switches itself off ~100 ms after activation on VS Code 1.143 and never recovers, so E2E runs record no `Trace` lines. Evidence: the log stops after the 5–7 activation lines; `getLogFile()` returns null while `git-graph-rs.enableLog` reads true in every scope (verified from the E2E entry: `.get()`, `inspect().globalValue/workspaceValue`, both with implicit and explicit-undefined scope); 60 real off→on configuration changes delivered as events during the run did not revive it; the same truncate the logger performs on enable succeeds from a plain Node process on the same path. The defect is in the extension's own enable path — `src/extension/platform/logger.ts`'s `setEnabled` (a failed initial truncate nulls `logFile` while `enabled` stays true, silencing the mirror forever) and/or `src/extension/main.ts`'s configuration listener (re-reads `enableLog` on any `git-graph-rs` change during the startup transient and acts on it). The harness side is done and verified: the entry repairs-and-polls, the launcher collects, the collector reports the absence explicitly instead of writing empty summaries. | the logger fix, then any E2E run |

The E2E smoke on this tree currently reports 22 passed / 1 failed / 2 skipped
(`external/commit-appears`: the watcher-driven refresh never reaches the page — undiagnosable
while the session log is dead, see the blocker above; the `data-gg-refresh` counter the action
prints is dead diagnostics — no code has ever set it).

## D-2 (retainContextWhenHidden)

Measured by the new perf tier (`npm run test:e2e -- --tier perf`, scenario `perf/D2-restore`,
2026-10-27, VS Code 1.143.1, Windows, engine read path): the procedure hides the view behind a
plain text editor, polls whether an in-page marker (the page's memory) survives the hidden
period, then times the reveal → commit-rows-visible — once with the setting at its default
(`true`), once flipped to `false` with a freshly created panel (VS Code reads the flag at panel
creation), restoring the setting afterwards.

| Position | Restore latency (reveal → rows visible) | Page fate while hidden |
|---|---|---|
| `retainContextWhenHidden: true` (default) | **52 ms** | survived (page and its memory intact) |
| `retainContextWhenHidden: false` | **227 ms** | disposed by VS Code within the observation window; the restore pays a full page boot |

**Recommendation: do not flip the default.** D-2's bar was "flip to `false` if the restore meets
the 150 ms snapshot-first-paint budget"; the non-retained restore measured 227 ms — the memory
saved per hidden panel does not pay for a restore that misses the budget on the reference
machine. The retained restore's 52 ms is far inside it. Revisit only if the restore path (D10
snapshots) gets under 150 ms measured, via this same scenario.

## Consequences

- `docs/performance.md`'s budget table gains these numbers and points here; its rows that this
  record could not measure stay `pending — measured by <P-gate>` per ADR-0004.
- The nightly owns the remaining calibration surface: M tier, CI Linux, and — after the logger
  fix — the in-editor traces. No budget number moves until then; after then, only tighter.
